Integration walkthrough · TASK-022

Connect an internal app

Your app sends the browser to BTAuthOrchestrator for sign-in, receives a shared bt_session cookie on a later browser request, and verifies its JWT on your server. Your app decides what that person may access.

Standalone documentation. Open this file directly in a browser; no server, build, internet connection, or live credentials are needed to view it. The diagrams and code are illustrative, not a running login client or SDK.

1. Browser flow2. Receive the session3. Verify on your server4. Local login5. Integration checks
01 / OIDC login · LOCAL_LOGIN=false

Send the browser to the orchestrator

Example consuming app: https://tools.biztechro.com. Example orchestrator: https://orca.biztechro.com. These are deployment examples; this file makes no network requests.

  1. Check the incoming session. If there is no valid session, redirect browser navigation to https://orca.biztechro.com/auth/login. Keep protected data unavailable until verification succeeds.
  2. Let the orchestrator handle OIDC. It owns Entra discovery, the state/nonce/PKCE handshake, code exchange, and ID-token validation. Entra's registered callback belongs to the orchestrator: https://orca.biztechro.com/auth/callback in production.
  3. Receive the orchestrator's cookie. Successful login returns HTTP 200 and “You're signed in. You may close this window.” The browser stores bt_session when the cookie's domain and transport requirements are met.
  4. Return to the app. The user revisits the app or refreshes an existing app tab. That request carries the shared cookie; your server verifies it before using its identity claims.
There is currently no app callback or return-to parameter. Do not expect a redirect back to your tool after sign-in. The success page is the current endpoint of the login journey.
02 / Browser → your server

Read the cookie on the server

Set-Cookie: bt_session=<signed JWT>; Domain=.biztechro.com; Path=/;
            HttpOnly; SameSite=Lax; Expires=<expiry>; Max-Age=<seconds>
            [Secure when COOKIE_SECURE=true]

# Later request to your app, sent by the browser:
Cookie: bt_session=<signed JWT>

Use your web framework's cookie parser on the incoming request. HttpOnly prevents browser JavaScript from reading this cookie; do not build the integration around document.cookie, localStorage, or a token in a URL.

What the consuming app verifies and uses
FieldMeaning
alg / kid (header)RS256 and the matching signing-key identifier in the orchestrator's JWKS.
issThe configured SERVICE_ISSUER; production is https://orca.biztechro.com. Configure the trusted expected value in your app.
sub / email / upnIdentity: Entra object ID, email, and preferred username. Use the verified issuer and subject as the identity key; email is not an authorization grant.
iat / expEpoch seconds. Expiry is the next midnight in the orchestrator host's local timezone, not a fixed 24-hour lifetime. Verify the absolute expiry normally.
aud / roles / groups / scopesAbsent by design. The token authenticates a person across the shared domain; your app owns authorization.
Localhost does not receive the shared-domain cookie. A response from localhost:3210 cannot set a cookie for .biztechro.com. Viewing this file and fetching health/JWKS work locally, but browser SSO requires suitable *.biztechro.com hostnames that resolve to your test services. Changing SERVICE_ISSUER does not change the fixed cookie domain. For OIDC, the registered Entra redirect URI must match the configured issuer plus /auth/callback. When COOKIE_SECURE=true, consuming apps need HTTPS; the flag is independent of NODE_ENV.
03 / Your server

Fetch public keys, then verify offline

Fetch /.well-known/jwks.json from a trusted orchestrator address. It supplies public signing keys; your app needs no orchestrator database, private signing key, client secret, or admin credential.

This Node.js example uses jose 6.x, the same library as the service. Save adapted code as an ES module in your consuming app. The HTML does not execute it.

// Illustrative Node.js ES module (.mjs), using jose 6.x.
// In the consuming app: npm install jose
import { createLocalJWKSet, jwtVerify } from 'jose';

// Trusted deployment settings, never values supplied by the JWT or request.
const expectedIssuer = 'https://orca.biztechro.com';
const jwksUrl = 'https://orca.biztechro.com/.well-known/jwks.json';

// Fetch once at app startup (or from an explicit refresh job).
const response = await fetch(jwksUrl, {
  signal: AbortSignal.timeout(5000),
  cache: 'no-store',
});
if (!response.ok) throw new Error('Unable to load signing keys');
const verifyKey = createLocalJWKSet(await response.json());

export async function verifySession(token) {
  // Your framework's server-side cookie parser supplies token from bt_session.
  if (typeof token !== 'string' || token.length === 0) {
    throw new Error('Sign-in required');
  }
  const { payload, protectedHeader } = await jwtVerify(token, verifyKey, {
    algorithms: ['RS256'],
    issuer: expectedIssuer,
    requiredClaims: ['sub', 'email', 'upn', 'iat', 'exp', 'iss'],
    // No audience option: these shared session tokens intentionally have no aud.
  });
  if (typeof protectedHeader.kid !== 'string' || !protectedHeader.kid) {
    throw new Error('Missing signing key ID');
  }
  for (const name of ['sub', 'email', 'upn']) {
    if (typeof payload[name] !== 'string' || !payload[name].trim()) {
      throw new Error('Invalid identity claims');
    }
  }
  if (typeof payload.iat !== 'number' || typeof payload.exp !== 'number'
      || payload.exp <= payload.iat) {
    throw new Error('Invalid session lifetime');
  }
  return { id: payload.sub, email: payload.email, username: payload.upn };
}

// } catch {

//   // API requests should receive an authentication error, not protected data.

Verification is not decoding. jwtVerify checks the signature and claims; merely parsing a JWT's payload provides no proof of identity. Do not select the trusted issuer or JWKS URL from an unverified token.

Offline has a freshness boundary. The example performs no network request inside verifySession; an already-loaded key set can verify known keys during an orchestrator outage. The JWKS endpoint sends Cache-Control: no-store; the example explicitly holds a process-local snapshot rather than relying on HTTP caching. Production integration needs an explicit key-refresh policy and bounded retry for an unknown kid. Reject a token if its key cannot be resolved. A stale snapshot does not learn that a key was removed until refreshed; this startup-only example is not a complete key-lifecycle client.

04 / Alternative · LOCAL_LOGIN=true

Local login, same consuming-app verification

Send the browser to /auth/local-login on the orchestrator instead of /auth/login. Its form submits JSON to the same origin:

POST /auth/local-login
Content-Type: application/json

{"username":"sample.user","password":"<user-entered password>"}

# Success: HTTP 200 + the same bt_session Set-Cookie header
{"status":"signed_in","username":"sample.user"}

The form stays on its success page. The user then returns to your app, which verifies the cookie exactly as above. Local tokens use the local user ID as sub, stored email as email, and username as upn. All signing, issuer, expiry, and cookie rules are shared.

The modes are exclusive: LOCAL_LOGIN=true disables OIDC login/callback routes; LOCAL_LOGIN=false disables local login. Calling a disabled login path returns 404. Invalid local credentials return 401; disabled, locked, and throttled attempts return 403, 423, and 429 respectively. No successful session should be inferred from those errors.

05 / Put the pieces together

Checks for your integration

  1. Reachability: request GET /health and GET /.well-known/jwks.json on your orchestrator. A health response confirms liveness, not a completed sign-in.
  2. Browser delivery: use the configured login mode and confirm the browser stores bt_session and sends it to your app's hostname. Check the domain and Secure setting if it does not.
  3. Trust: configure the expected issuer and trusted JWKS endpoint in your app, and accept only RS256 signatures with the expected identity claims.
  4. Failure handling: missing, tampered, expired, wrong-issuer, or unknown-key tokens must not unlock protected data. An expired session requires another sign-in; no refresh-token flow is implemented.
  5. Authorization: a valid session establishes identity. Check your own access rules separately.

Documentation scope: current CONTRACT-001 and CONTRACT-005 flows, with the implemented configurable issuer from TASK-012. No service changes are required to view this walkthrough. Live OIDC additionally needs configured Entra registration and reachable callback infrastructure.
